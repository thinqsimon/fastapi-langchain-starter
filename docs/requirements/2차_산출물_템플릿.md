## 1. 서비스 기획 및 아키텍처 설계서

### 무엇을 작성하나요?

프로젝트에서 구축한 AI 서비스 스타터킷의 전체 구조와 재사용을 위한 설계 의도를 설명합니다.

코드를 자세히 설명하기보다,

> **"스타터킷에 무엇이 포함되어 있고, 각 모듈이 어떻게 연결되며, 새 서비스를 만들 때 무엇을 바꾸면 되는가?"**

를 중심으로 작성합니다.

### 필수 작성 항목

#### ① 프로젝트 개요

아래 내용을 간단하게 작성합니다.

- 스타터킷 주제 및 목적
- 해결하고자 하는 문제 (새 AI 서비스를 시작할 때 반복되는 작업)
- 대상 사용자 (스타터킷을 Fork해 사용하는 개발자)
- 기술 스택 (FastAPI, React, PostgreSQL, LangChain 등)
- 사용한 LLM API 또는 모델

**작성 예시**

| 항목 | 내용 |
|---|---|
| 프로젝트 주제 | 챗봇형 AI 서비스 스타터킷 |
| 스타터킷 설명 | 인증, 대화 이력 저장, LLM 스트리밍 응답, CI/CD 배포 설정이 포함되어 Fork 후 바로 챗봇형 AI 서비스를 시작할 수 있는 보일러플레이트입니다. |
| 사용 모델 | OpenAI GPT API 기반 LangChain 연동 |

#### ② 전체 아키텍처

스타터킷 구조를 한 장의 그림으로 표현합니다. 아래 요소가 포함되도록 구성합니다.

- React 프론트엔드
- FastAPI 백엔드 (계층 구조)
- PostgreSQL 데이터베이스
- LangChain 기반 LLM 연동 모듈
- GitHub Actions CI/CD 파이프라인
- 배포 환경

**예시 흐름**

```
사용자 → React → FastAPI → PostgreSQL / LangChain → LLM API → 응답
```

배포 흐름은 다음과 같이 별도로 표현해도 좋습니다.

```
코드 Push → GitHub Actions (빌드·테스트) → 배포 게이트 → 자동 배포
```

#### ③ 디렉터리 구조 및 모듈 설명

스타터킷의 폴더 구조와 각 모듈의 역할을 설명합니다.

예시:

```
starter-kit/
├── backend/        # FastAPI (routers / services / repositories)
├── frontend/       # React
├── .github/        # GitHub Actions 워크플로우
├── docs/           # 설계서, 사용 가이드
└── .env.example    # 환경 변수 예시
```

각 모듈에 대해 아래 내용을 함께 정리합니다.

- 이 모듈이 맡는 역할
- 새 서비스에서 그대로 쓰는 부분과 수정해야 하는 부분

#### ④ 사용자 요청 흐름 설명

샘플 서비스에서 사용자 요청이 처리되는 흐름을 설명합니다.

예시:

1. 사용자가 로그인해 JWT를 발급받습니다.
2. 프론트엔드가 토큰과 함께 API를 호출합니다.
3. 백엔드가 토큰을 검증하고 서비스 계층을 호출합니다.
4. 필요한 데이터를 DB에서 조회하고 LLM 연동 모듈을 호출합니다.
5. LLM 응답을 가공해 프론트엔드에 반환합니다.
6. 프론트엔드가 결과를 화면에 표시합니다.

#### ⑤ CI/CD 파이프라인 설계

자동화 단계와 배포 기준을 정리합니다.

예시:

| 단계 | 내용 | 실패 시 처리 |
|---|---|---|
| 빌드 | 백엔드·프론트엔드 빌드 | 배포 중단 |
| 테스트 | API·E2E 테스트 실행 | 배포 중단 |
| 배포 게이트 | 테스트 통과 여부 확인 | 배포 중단 |
| 배포 | 자동 배포 및 상태 확인 | 이전 버전 유지 |

#### ⑥ 주요 설계 결정

프로젝트에서 중요하게 결정한 내용을 정리합니다.

예시:

- 스타터킷에 어떤 기능을 포함하고 어떤 기능을 제외했는지
- 계층 구조를 이렇게 나눈 이유
- 설정과 비밀 값(API Key 등)을 어떻게 분리했는지
- LLM 연동 모듈을 교체·확장하기 쉽게 만든 방법
- CI/CD에서 어떤 품질 기준을 배포 게이트로 정했는지

> 모든 기능을 다 넣는 것이 목표가 아닙니다.
> 스타터킷을 Fork한 사람에게 **왜 이 구성이 필요한지**를 설명할 수 있는 것이 중요합니다.

### 제출 형태

다음 중 하나로 제출합니다.

- Notion 문서
- PDF
- Git Repository 내 `/docs/architecture.md`

아키텍처 이미지는 PNG, JPG 또는 Mermaid 등 자유롭게 사용할 수 있습니다.

## 2. 스타터킷 사용 및 운영 가이드

### 무엇을 작성하나요?

스타터킷을 처음 접하는 개발자가 Fork한 뒤 문서만 보고 실행·커스터마이징·배포할 수 있도록 설명합니다.

- "처음 스타터킷을 실행하는 방법"
- "새 서비스로 바꾸는 방법"
- "문제가 생겼을 때 가장 먼저 확인할 것"

### 권장 문서 구성

#### ① 실행 전 준비

예시:

- Python·Node 버전 확인
- PostgreSQL 준비 및 접속 정보
- LLM API Key 등 환경 변수 준비 (`.env.example` 복사)
- 필요한 패키지 설치

#### ② 스타터킷 Fork 및 실행

실제로 사용한 명령어를 순서대로 작성합니다.

예시:

```bash
git clone <Fork한 저장소 주소>
cp .env.example .env
pip install -r backend/requirements.txt
alembic upgrade head
uvicorn main:app --reload
npm install && npm run dev
```

#### ③ 실행 상태 확인

예시:

```bash
curl http://localhost:8000/health
```

무엇이 출력되면 정상인지 함께 설명합니다.

#### ④ 서비스 정상 동작 확인

다음 항목을 확인합니다.

- 회원가입·로그인이 정상 동작하는지
- 인증이 필요한 API가 토큰 없이 접근 시 차단되는지
- LLM 연동 API가 정상 응답하는지
- 프론트엔드 화면에서 샘플 서비스가 동작하는지

예시:

```bash
curl -X POST http://localhost:8000/api/chat \
  -H "Authorization: Bearer <토큰>" \
  -d '{"message": "안녕"}'
```

예상 결과:

```json
{
  "status": "ok",
  "reply": "..."
}
```

#### ⑤ 로그 확인

예시:

```bash
tail -f logs/app.log
```

백엔드·프론트엔드 로그를 각각 어디서 확인하는지도 설명합니다.

#### ⑥ 새 서비스로 커스터마이징

스타터킷을 새 서비스로 바꾸는 방법을 작성합니다.

예시:

1. 프로젝트명·환경 변수 변경
2. 도메인에 맞게 DB 모델 수정 후 마이그레이션 생성
3. 서비스 계층·프롬프트 템플릿 교체
4. 프론트엔드 화면 수정
5. 테스트 수정 후 실행

#### ⑦ CI/CD 확인 및 배포

예시:

```
git push origin main
→ GitHub Actions 실행 확인
→ 빌드·테스트 통과 확인
→ 배포 게이트 통과 확인
→ 배포된 서비스 정상 동작 확인
```

필요한 Secret 등록 방법(GitHub Secrets 등)과 배포 실패 시 확인 위치도 함께 설명합니다.

#### ⑧ 재배포 또는 업데이트

새로운 코드 버전을 배포하는 방법을 작성합니다.

예시:

```
v1 → v2 코드 변경
→ 마이그레이션 적용
→ 재빌드 및 재배포
→ API 정상 동작 확인
→ 화면 정상 표시 확인
```

#### ⑨ 장애 발생 시 기본 점검 순서

권장 순서:

1. 백엔드 서버 상태 확인
2. 데이터베이스 연결·마이그레이션 상태 확인
3. LLM API 응답·에러 확인
4. Application Log 확인
5. 프론트엔드 콘솔 에러 확인
6. 환경 변수·Secret 설정 확인
7. CI/CD 실행 로그 확인
