# ADR-0007: 공통 스타터킷과 배움일기 코치를 실행 프로필로 분리

- 날짜: 2026-10-26
- 상태: 채택
- 브랜치: `service/diary-coach`

## 배경

기존 `main`에는 일기·개인 화면 설정 API, 서비스 이름과 메뉴가 항상 등록된다.
`samples/diary-coach`는 설명 문서이며 독립 실행 앱이 아니다. 초기화 스크립트로 샘플을
삭제해도 import와 메뉴를 사람이 정리해야 하므로 공통 기반을 바로 실행하기 어렵다.

## 결정

코드를 복제하거나 대규모로 이동하지 않고 실행 프로필과 조립 지점을 추가한다.

| 프로필 | 공통 기능 | 서비스 기능 |
|---|---|---|
| `starter` | 인증·계정 수정, 대화·SSE, LLM 연결, 사용량, 선택 RAG | 없음 |
| `diary-coach` | 같은 공통 기능 | 일기·회고, 캐치프레이즈·일기 푸터 |

백엔드 `application.py`에서 기능과 시스템 프롬프트를 선택하고 `api.py`에서 라우터를 조립한다.
선택은 앱 생성 시 고정하며 앱 인스턴스마다 보관한다. 공통 ChatService는 주입받은 프롬프트를
사용한다. core/domain에 배움일기 프로필 분기나 도메인 역방향 의존을 추가하지 않는다.

프론트엔드는 프로필별 이름·설명·기능과 서비스 UI 슬롯을 조립한다. starter에서 메뉴를 숨기는
것에 더해 `/diary` 직접 접근도 404로 처리하고, 서비스 설정 API를 호출하지 않는다.
공통 계정 설정은 두 프로필에서 계속 사용할 수 있다.

`APP_PROFILE`은 백엔드 시작 시, `NEXT_PUBLIC_APP_PROFILE`은 프론트엔드 빌드 시 적용한다.
브랜치 이름으로 프로필을 추측하지 않는다. 개발 런처는 양쪽에 같은 값을 전달한다.
기존 실행 환경의 호환성을 위해 기본값은 두 곳 모두 `diary-coach`로 둔다.

## DB와 기존 데이터

실행 기능 분리와 물리적인 DB 스키마 분리는 별개다. 이번 변경은 전자만 수행한다.
모든 ORM 모델과 적용된 Alembic 마이그레이션을 보존한다. starter에서도 샘플 테이블이
존재할 수 있지만 서비스 API는 등록하지 않는다. 프로필을 바꿔도 테이블을 삭제하거나
`alembic autogenerate`가 기존 일기 테이블을 삭제 대상으로 판단하도록 만들지 않는다.
신규 프로젝트의 별도 마이그레이션 기준선은 후속 작업에서 독립적으로 설계한다.

## 브랜치와 배포

`main`을 안정 기준으로 두고 `service/diary-coach`에서 서비스 개발을 진행한다.
공통으로 재사용할 변경은 이후 작은 PR로 선별해 main에 반영한다.
서비스 전체를 main에 통째로 병합하지 않는다.

서비스 브랜치 push에서도 CI를 실행하고 두 프로필의 화면 흐름을 검사한다.
현재 운영 배포의 main 게이트와 Render/Vercel 설정은 이번 작업에서 변경하지 않는다.
서비스 배포 전 대상 브랜치·환경·검증한 커밋 일치를 별도로 확인한다.

## 검증 기준

1. starter에는 인증·채팅·사용량이 있고 일기·전용 설정 API와 메뉴는 없다.
2. starter의 일기 URL 직접 접근은 404이며 전용 개인 설정 요청도 발생하지 않는다.
3. diary-coach의 기존 일기·회고·개인 설정과 인증 흐름은 유지된다.
4. 공통 채팅은 두 프로필에서 동작하고 각 프로필의 프롬프트를 사용한다.
5. 기존 DB 모델·마이그레이션 이력은 동일하게 보존된다.
6. 린트·타입·계층 규칙·테스트·빌드와 두 프로필 E2E를 확인한다.
